## 痛点：为什么"加载好了"不等于"能调函数"？

你按第 1 章把军棋 so 搬进 unidbg（mmap + 重定位 + 跑 12 个 init_array 全通），
觉得"能跑了"。但一调 `OnCreate` 就发现**"加载成功"和"能调通"是两回事**。

**痛点 1：函数入口在哪？（strip 后符号表空）**
军棋 so 是 stripped（删除符号信息），`.dynsym` 里只剩 14 个 `Java_com_cnvcs_App_On*` 导出符号，
内部函数（比如"翻棋判定"）全没名字。你想调一个内部函数，得先**静态分析找出它的入口地址**，
再用"地址调用"。

**★ 没有符号"猜"函数用途 = 3 层工具（不是盲猜，追问 ②）**：
军棋 `.text`/`.rodata` 是**明文**（熵 7.10，非壳），`objdump` 可直接反汇编，**静态推断是主力**，unidbg 动态是"交叉校验"：
| 手段 | 军棋实战 | 能到什么程度 |
|---|---|---|
| **静态反汇编 + 字符串引用** | 军棋 `.rodata` 明文（1715 串），函数调 `FindClass("com/baidu/mobads/AdView")` → 八成是"广告初始化" | 靠明文串/常量反推函数用途，不用盲猜 |
| **静态调用图（谁调谁）** | `objdump` 解析 `bl`/`blx` 指令 → 画调用图；`OnCreate` 调 `0x39e14` → 推断 0x39e14 是"对局初始化" | 靠控制流/调用关系推断 |
| **unidbg 动态验证（防骨架画错）** | 跑 `OnCreate` 看真实 PC 流（`DiagTracePC`/Stalker），**交叉验证静态调用图对不对**（静态说 A 调 B，动态看 A 是否真走到 B） | **静态是骨架，动态是"防骨架画错"的校验层** |
**结论**：军棋 R-route 把核心函数（0x39e14/0x6a3b0/0x302b4）的"控制流 + 常量 + 布局 + 业务名"**全静态逆向成结论表**（`R-route_reversal.md`），unidbg 动态只是"验骨架没画错"——**不是"没符号只能盲猜"**。

**痛点 2：参数怎么传？（指针要手动构造）**
军棋 `OnCreate(JNIEnv *env, jobject obj)` 要两个指针参数：
- `JNIEnv*`：一张 232 个函数指针的表（JNI 接口表），不是普通指针
- `jobject`：Java 对象的"哈希"（DalvikVM 里对象的引用），不是 C++ 对象指针

模拟环境里这两个都要**手动构造**，传错了 so 就崩。

**★ 关键澄清（读者最易卡点）：`JNIEnv*` 与 `Java_` 导出符号是两个独立方向，别混**

JNI 是"Java 与 native 的双向桥"，两个方向**走的是完全不同的通道**：

| 方向 | 走什么 | 军棋对应 | 谁提供 |
|---|---|---|---|
| **① Java → so** | `Java_` 前缀**导出符号**（命名约定 `Java_com_cnvcs_App_OnCreate` ↔ Java 侧 `com.cnvcs.App.OnCreate`） | VM dlopen so 后按符号/注册表把 Java 方法**绑定**到 so 导出函数；调用时**直接跳 so 里的函数地址**（unidbg 用 `call(0x233e1)` 模拟这个绑定） | **so 导出**（军棋 14 个 `On*`），VM 负责绑定 |
| **② so → Java** | `JNIEnv*`（指向一张 **232 槽 C API 函数表**） | so 拿到 `env` 后 `env->FindClass(...)` / `env->CallVoidMethod(...)` 跳表间接访问 Java 类/方法/对象 | **VM 提供**（libdvm/libart 的 C++ 实现），so 只是**消费**这张表 |

- **`JNIEnv*` 是方向 ② 的唯一入口**：232 个槽是 **VM 实现的 JNI 标准 C API**（C++ 代码在 `libdvm`/`libart`，**不是 Java 方法、也不是 so 的函数**），功能是"让 native 间接操作 Java VM（找类/找方法/调方法/读写对象）"。
- **`Java_` 前缀符号是方向 ① 的门牌**：so 只需**导出**这些符号，VM 加载 so 时建立 `Java_...OnCreate` ↔ `com.cnvcs.App.OnCreate` 绑定，调用时**直接调 so 里的函数**，跟 `JNIEnv*` 无关。
- **unidbg 对应实现**：方向 ① 用地址调用 `call(0x233e1, ...)` 模拟"VM 绑定并调 so 导出函数"；方向 ② 用 `vm.getJNIEnv()` 返回的**模拟 JNIEnv 表**（232 槽全指向 unidbg 自己写的 C 模拟实现，背后接 `vm.setJni(this)` 你注册的 Java 侧应答）——模拟环境里**根本没有真 `libart`**，232 个槽没有任何一个是真机 VM 的地址。
- **易混点**：`jobject`（`OnCreate` 第 2 个参数）≠ `JNIEnv*`。`jobject` 是 **Java 对象句柄**（方向 ② 里 so 通过 `env->GetObjectClass(obj)` 等 API 去读的对象引用）；`JNIEnv*` 是**操作 VM 的 C API 入口表**。两者都是"so 调 Java"方向的料，但一个是指针表、一个是对象句柄。

**痛点 3：so 内部调 Java / 读文件 / 调 libc，谁来应答？（缺一个就崩）**
so 跑到一半 `FindClass("java/lang/String")` / `open("data/config/ui.xml")` / `strlen(...)`，
你的 unidbg 环境没人应答就崩。这是"补环境"的核心。

**痛点 4：军棋 14 个 JNI 入口是"Thumb 奇地址"，调用前要 `&~1` 对齐**（这是军棋特有的坑，下面细讲；★ 是 arm32 特有，arm64 没有——见下"两种指令集"）。

## 为什么这样做：符号调用 vs 地址调用，军棋只能走"地址调用"

书里两种调法：

| 调法 | 适合 | 军棋能不能用 |
|---|---|---|
| **符号调用**（`findSymbol("funcName")`） | 符号表完整的 so（书内样本） | ❌ 军棋 strip 后符号表只剩 14 个 `On*`，内部函数没名字 |
| **地址调用**（`call(0x233e1, ...)`） | strip 的 so / 调内部函数 | ✅ 军棋走这条（14 个 `On*` 入口有地址，内部函数靠 IDA 找） |

**军棋为什么 14 个入口是"奇地址"（关键坑）**：

军棋 so 是 ARM/Thumb 混合编译。JNI 注册表（`.dynsym`）里存的函数地址是"奇数"
（比如 `OnCreate = 0x233e1`），bit0=1 表示"跳 Thumb 模式"。

```
0x233e1 (奇数, Thumb 模式)
  bit0 = 1  →  告诉 CPU "下一条指令是 16 位 Thumb 指令"
  实际执行起点 = 0x233e1 & ~1 = 0x233e0 (偶数)
```

**调用前必须 `&~1` 对齐到偶指令**，否则翻译器（unidbg 的指令分析）可达集为空 →
跑出 0KB 函数体（军棋红线 §R6：JNI 入口是 Thumb 奇地址，不在偶指令表，
`translate_func` 起点要 bisect 对齐到最近偶指令，否则可达集空 → 0KB body）。

类比：门牌号是"奇数"（带 Thumb 标志），但开门要按"偶数"门（实际指令起点），
拿错门牌进不去。

### ★ 两种指令集（追问：ARM 同时支持两种？arm64 呢？怎么判断？）

**架构级差异（读者最易卡点）**：

| 架构 | 指令集 | 奇地址/&~1 问题 | 说明 |
|---|---|---|---|
| **ARMv7（32 位）** | **同一架构同时支持 ARM + Thumb 两种指令集** | **有**（函数地址可奇可偶，bit0 是模式标志） | CPU 靠 **CPSR.T 位**在 ARM/Thumb 间切换；**一条 so 可混编**（军棋 `.text` = ARM+Thumb 混合） |
| **AArch64（64 位）** | **架构级只剩一种"指令流"**（取消了 T 位切换） | **没有**（函数地址恒为偶数，无奇地址问题） | 但指令编码仍有 16 位（Thumb-2 形式）/ 32 位两种，**全部 4 字节对齐**；**64 位地址调用直接传偶地址即可，无需 `&~1`** |

**★ 结论**：军棋"Thumb 奇地址 + `&~1` 对齐"是 **arm32（ARMv7）特有**；**arm64（AArch64）没有奇地址**（64 位地址调用传 `0x233e0` 类偶地址即可，bit0 永远是 0）。

**"在 so 里怎么知道某段指令是 Thumb 还是 ARM"（追问）**：
- **不靠段属性**（ELF `.text` 段的 `SHF_EXECINSTR` 只说"可执行"，不说 ARM/Thumb）
- **靠函数入口地址的 bit0**（`.dynsym` 里 `OnCreate = 0x233e1` 奇数 = Thumb；内部函数靠 IDA 函数边界识别）
- **靠反汇编器**：`objdump -d` 看某地址指令是 16 位（Thumb）还是 32 位（ARM）编码 → 判定该区域
- **混合编译时**：`.text` 段里 ARM 函数和 Thumb 函数**混在一起**，**区分靠每个函数入口的 bit0**

**unidbg 怎么知道是 Thumb（追问）**：**靠你传入地址的 bit0**——
- 传 `0x233e1`（奇，bit0=1）→ unidbg 设 **CPU T 位 = 1** → 按 **Thumb 解码器**解 0x233e0 起字节
- 传 `0x233e0`（偶，bit0=0）→ unidbg 设 **T 位 = 0** → 按 **ARM 解码器**解
- **bit0 是"模式开关"，不是"地址的一部分"**：`call(0x233e1)` unidbg 取指 `0x233e1 & ~1 = 0x233e0`，但**用 Thumb 解码器**（bit0=1 告知）
- **传错会怎样**：传 `0x233e0`（丢 bit0）→ T=0，**ARM 解码器去解 Thumb 指令** → 解码垃圾 → 执行错乱
- **两个场景的 `&~1` 别混**：unidbg 动态 `call()` 传奇地址（内部自动对齐 T 位）；**静态反汇编生成 C（gen_shadow.py）函数起点要 `&~1` 对齐到偶指令**（否则可达集空 → 0KB body）——前者是"模式标志"，后者是"指令边界"

## 2.2 军棋地址调用实战（逐环节能干什么）


> **本节核心**：
> 1. 4 步：findSymbol(&~1) → 构造参数（env + obj）→ call → 验返回
> 2. 军棋 14 入口是 Thumb 奇地址（0x233e1），调用前 &~1 对齐，否则可达集空
> 3. OnCreate(env, obj)：env=getJNIEnv()（JNI 函数表 232 槽），obj=addGlobalObject(DvmObject)
>
> **本节难点**：
> 1. 军棋 DiagJni：OnCreate 推进到 std::vector 拷贝构造点 0x43ed8（§124 ② "数据与指令对齐对应"卡点，N44）
> 2. 「&~1 对齐」是军棋特有坑：奇地址不在偶指令表，translate_func 起点 bisect 对齐

![符号调用 vs 地址调用](assets/ch02_symbol_vs_addr.png)


![主动调用 4 步前置](assets/ch02_call_prepare.png)

军棋调 `OnCreate` 的完整路径（军棋实测可跑通）：

```java
// 前置 4 步(军棋实测全通)
// 1. 加载 so(跑 12 个 .init_array + 重定位)
DalvikModule dm = vm.loadLibrary(new File("lib/armeabi/libjunqi.so"), true);

// 2. 注册 Java 侧应答(找类/找方法/调方法)
vm.setJni(this);  // this 实现 Jni 接口:findClass/getMethodID/callXxxMethod*

// 3. 跑 JNI_OnLoad(so 的开机自检,注册 14 个 On* 方法)
vm.callJNI_OnLoad(emulator, dm.getModule());

// 4. 构造参数 + 按地址调 OnCreate(Thumb 奇地址 0x233e1)
Pointer jniEnv = vm.getJNIEnv();            // JNIEnv*(232 函数表)
int objHash = vm.addGlobalObject(new DvmObject<>());  // jobject(哈希)
long ret = vm.getMemory().call(emulator, 0x233e1L, 0, jniEnv, objHash).singleValue();
// 军棋 DiagJni:OnCreate 推进到 std::vector 拷贝构造点 0x43ed8(§124 三项阻塞卡在这)
```

### 逐环节"我们能干什么 / 不能干什么"


> **本节核心**：
> 1. 能/不能表：地址调用能找 14 入口、构造指针参数、验返回值
> 2. 不能：单步穿越 §124 三项阻塞（读未初始化值必崩被安全阀兜成 0）
>
> **本节难点**：
> 1. 地址调用「能调」≠「调通」：调 OnCreate 推进到 0x43ed8 后 §124 ② "数据与指令对齐对应"缺口卡住（N44）
> 2. 构造参数错（jobject 当 int 传）就崩，军棋 14 入口签名不统一

| 环节 | 能干什么（✓） | 不能干什么（✗） |
|---|---|---|
| **找入口** | 按地址调 14 个 `On*`（strip 后唯一门牌）；内部函数用 IDA 找地址 | 按符号调内部函数（符号表空） |
| **对齐入口** | `&~1` 把 Thumb 奇地址对齐到偶指令（军棋红线 §R6） | 不对齐直接调（可达集空 → 0KB body） |
| **构造 JNIEnv\*** | `vm.getJNIEnv()` 拿模拟的 232 槽 **VM 标准 C API 表**（方向 ② so→Java 唯一入口，全指 unidbg 模拟实现，背后接 `setJni`；非真 `libart` 地址、非 Java 方法） | 用真机的 `JNIEnv*`（模拟环境没有）；**别把"so 被调用"（方向 ①，`Java_` 导出符号 / `call(0x233e1)` 地址调用）和"so 调 Java"（方向 ②，`env->Xxx` 跳 232 槽表）混成一个方向** |
| **构造 jobject** | `vm.addGlobalObject(new DvmObject<>())` 注册拿哈希 | 传真 C++ 对象（DalvikVM 里是"哈希"不是对象指针） |
| **调函数** | 地址调用 `call(0x233e1, ...)` | 突破 0x43ed8（§124 三项阻塞：① BL 解码 bug ② 数据与指令对齐缺口 ③ 288MB mmap） |
| **应答内部调用** | `setJni` 实现 `findClass`/`getMethodID`/`callXxxMethod`（军棋 AdView 返 null 去广告） | 完整数据与指令对齐（std::vector 运行时布局未填，N44） |
## 2.3 军棋的卡点：18 个 `.text` 常量（读得出门牌号，读不出房间真值）


> **本节核心**：
> 1. 18 个 .text 常量（15 .text + 2 .data = 72B）槽**静态读得出**，但读出的是**门牌号**（如 `.so` 文件偏移 `0x138918`），跟着门牌号进的"房间真值"（redroid 运行时绝对地址 `0x96a779e4` 类）才是 dlopen 重定位才填对
> 2. **★ 术语纠正（N45：推翻旧"静态读不出"错误概括）**：类比 `open("/data/img/1.png")`——代码存的是**路径（门牌号）**，不是**图片像素（数据本身）**；18 常量存的是"重定位目标占位"（门牌号），不是"重定位后的真地址"（房间真值）。**不是"读不出"，是"读出的是门牌号而非房间真值"**
> 3. .so 未重定位时，`.got`/RELATIVE 槽是零/占位，**门牌号指向的"房间"在静态文件里是占位值**（如 `0x96a779e4` = redroid 某次 dlopen 的运行时基址，不同进程不同）
>
> **本节难点**：
> 1. 两个方向都断 → 早期拿法 = redroid 跑原版 dump 72B"房间真值"注入（工具三件套）；**★ §124x-z 后演进为"静态位移固化 `jqt_mem.c` `g_jq_got_tbl`"（把"门牌号→静态位移"固化，无需运行时 dump，见 2.3 路线演进表）**
> 2. 18 个常量是「仅 dlopen 重定位填房间真值」，非壳自解密（已证 .rodata 静态即明文，门牌号本身静态可读）
> 3. redroid dump 工具：frida-dump/redroid_jni_dump.py 读 18 地址 + gen_runtime_table.py JSON→C

军棋 `OnCreate` 一调，就卡在**运行时 18 个地址的"房间真值"**上（红线 §R6）：
```
军棋 14 个 JNI 入口内部:
  ldr rX, [pc, #N]   →  读 .text 内嵌常量池 0xbd10f…（读的是"门牌号"）
  
  门牌号静态可读（.so 文件偏移，如 0x0235c4 槽存 0x00138918）
  跟着门牌号进去的"房间真值" = dlopen 重定位后才填对（.so 静态文件里是占位，
  如 0x138918 处存 0x96a779e4 = redroid 某次 dlopen 的运行时绝对地址，非 .so 内偏移）
  军棋 15 个 .text 常量池地址 + 2 个 .data 地址 = 共 18 地址 × 4B = 72 字节
```

**★ N45 术语纠正（推翻旧"静态读不出"）**：
- **旧表述（错）**："18 常量静态读不出（.so 文件里是零/密文）"——**混淆了"读不出"和"读出的是门牌号而非数据本身"**
- **正确表述**：18 常量槽**静态读得出**（门牌号 = `.so` 文件偏移，如 `0x0235c4` 处读 `0x00138918`），但**跟着门牌号进的"房间真值"在静态文件里是占位**（`0x138918` 处读 `0x96a779e4`，这是 redroid 某次 dlopen 的运行时基址，**不同进程/不同机器不同**，不是 .so 文件内的有效偏移）
- **类比（用户举的例子）**：代码里 `open("/data/img/1.png")`，`.text` 存的是**路径字符串 `"/data/img/1.png"`（门牌号）**，**不是 1.png 的像素数据（房间真值）**；同理 18 常量存的是**"重定位目标占位"（门牌号）**，**不是"重定位后的真地址"（房间真值）**——**门牌号静态可读，房间真值只有 dlopen 才填对**
- **军棋 .rodata 路径串实证**（你说的例子的真实对应）：`strings 军棋.so` 直接读出 `data/config/ui.xml` / `data/config/font.xml` / `data/lay/%02d.lay` 等**路径门牌号**（静态明文可读），**但跟着路径 open 出来的 `.xml` 文件内容（房间真值）在 apk 的 assets 里，不在 so 里**——**门牌号（so 里）和房间真值（资源文件里）是两层**

**★ N45 延伸（用户指出的关键点）：`.text` 常量缺失的"房间真值" = apk 的 SPAK 资源，能很清楚地知道在哪**
- 军棋 `.text` 常量（门牌号）指向的"房间真值"**几乎全是 apk 的 SPAK 资源包**（`assets/data*.pak`，`datah*.pak`/`data*.pak`/`datax*.pak` 等），**so 里只有路径/索引门牌号，资源真值在 .pak 里**：

  | 音效清单（`data/config/sound.xml`） | `assets/data*.pak` → 解包 → 14 个 WAV（`jq_sfx/*.wav`） |
  | 配置串（`data/config/*.xml`） | `assets/data*.pak` → 解包 → ui/font/image/string/path.xml |
- **★ 关键认知**：军棋 `.text` 常量"缺失"的**不是 so 里的神秘数据**，**而是"资源真值在 apk 的 .pak 里"这件事很清楚**——**门牌号（so）→ 跟着门牌号去 apk 的 .pak 解包 → 拿资源真值**（`spak_unpack.py` 已固化，`dist/spak_res/` 有解包产物）。**所以"`.text 缺失的东西可以很清楚地知道就是 apk 里的其他资源"**——**缺口不在 so 内部，在 apk 资源包，且解包工具链已固化**
- **与 N44 三层分工呼应**：**业务数据 apk 静态可推**（N44）的"可推"主要指**这层"门牌号→.pak 资源真值"的对应关系清楚**（不是运行时不可知），**缺的只是"运行时内存对齐"（翻译体补不齐）**

**为什么"房间真值"静态读不对**：
- `.rodata` 的**门牌号**（如路径字符串、常量池地址）是明文（已证 0/118832 不同，无自解密）——**这部分静态能读**
- 但 **18 常量槽跟着门牌号进的"房间真值"**（重定位后的真地址）**只有 dlopen 重定位后才填对**——**静态文件里是占位值**（`0x96a779e4` 类 = redroid 某次 dlopen 基址，**跨进程不可复现**，dlopen 每次基址随机化 ASLR）
**军棋拿这 18 个"房间真值"的办法（红线 §R6 工具三件套）——★ 路线演进（§124x-z 后，ch02 原文写"唯一办法 = redroid dump"已废弃）**：

| 阶段 | 办法 | 现状 |
|---|---|---|
| **早期（工具三件套）** | redroid 容器跑原版 32 位 so → dlopen → dump 18 个"房间真值"（常量池 + .data 共 72B 运行时值，非门牌号）→ 注入 unidbg。工具：`frida-dump/redroid_jni_dump.py` + `redroid_dump_jni.sh` + `gen_runtime_table.py`（JSON→C） | **保留作备查**（能 dump 但 redroid 32 位 so 不被加载 + 无 GPU，见 AGENTS.md 终局反思） |
| **★ 当前（§124x-z 静态固化）** | **18 值已静态固化在 `rev64/reverse/src_jni_translated/jqt_mem.c` 的 `g_jq_got_tbl`（静态位移，如 0x00138918，非 redroid 绝对值，不同进程基址通用），无需运行时 dump** | **当前干活会话直接用 `jqt_mem.c` 固化值，别再找/生成 `jni_runtime_values.json`（已删）** |

**★ 为什么改静态位移**：翻译体把 `add rX,pc` 实现为 `rX=file_off+rX`（PC 相对位移），故注入值应为**静态位移**（jq_img.bin 原始值），非 redroid 运行时绝对地址（`0x96a779e4` 类——不同进程基址不同，注入即错）。旧表用 redroid 绝对值 → 落到 host 随机映射读垃圾 → 主线程 `_ZdlPv(垃圾)` SIGSEGV。

**注意 §124 纠正**：拿到这 18 个值只是"指令能跑"，"能玩"还卡在 §124 的 3 项阻塞
（① 上下文相关 BL 解码 bug ② 数据与指令对齐对应缺口（业务数据 apk 静态可推，缺运行时对齐，N44 纠正原"对象图"措辞） ③ 288MB PROT_NONE mmap）。

## 2.4 军棋实战验证（地址调用 + 18 常量 + §124 阻塞）


> **本节核心**：
> 1. 地址调用 + 18 常量 + §124 阻塞全链路：OnCreate 推进 0x43ed8 卡住
> 2. 前 3 层补环境全通（系统调用/Java/指令），第 4 层数据与指令对齐补不了（N44：业务数据 apk 静态可推，缺运行时对齐 + 真机 C++ 构造链）
> 3. **双方向桥模型**：`Java_` 导出符号 = "Java 调 so"门牌（方向 ①，VM 绑定 + 直接调 so 函数）；`JNIEnv*` 232 槽 = "so 调 Java"中间层（方向 ②，VM 标准 C API，unidbg 模拟实现）——**两方向独立，别混**
> 4. **"§124 卡住"精确含义 = 数据错位（非崩溃）**：调通了但数据没对上（② 数据与指令对齐缺口），不是"调不通"
>
> **本节难点**：
> 1. 「能加载 ≠ 能调用」：12 init_array 全通但 OnCreate 卡 §124
> 2. §124 三项：① BL bug（模拟器精度）② 数据与指令对齐缺口（N44）③ 288MB mmap，补环境解决不了
> 3. "常量池全是公开常量？"——**军棋常量池混着 3 类"非公开业务数据"**（②③④ 在 so 静态可读值、① 在 .pak 资源；值能读，语义要 R-route 逆向）

**"§124 卡住"的精确含义（不是程序报错崩溃，是"调通了但数据错位"）**：

> **★ 术语纠正（N44：§124 ② 的准确表述 = "数据与指令对齐对应"，非"对象图不可知"）**
> 军棋卡点**不是"运行时凭空 new 的活对象不可知"**，而是：**业务数据（棋子数/布局/规则阈值）在 apk 里静态可推七七八八，缺的是"运行时让指令读的位置和数据填的位置对齐对应"（翻译体/unidbg 补不齐真实内存布局，需 frida dump 真值或真机 C++ 构造链填）**。
> 精确表述：**§124 ② = "数据与指令对齐对应"缺口**（业务数据静态在，运行时内存布局没对上），**不是"对象图凭空不可知"**。

| §124 阻塞 | "卡住"的具体表现 | 是崩溃还是 |
|---|---|---|
| ① BL 解码 bug | 执行流错位跳非函数入口（如 0x7965a 的 `bl` 误跳 0x6eaea 而非 0x10000004）→ 读到未初始化值 | **死循环/越界读**（安全阀兜住，非 SIGSEGV） |
| ② **数据与指令对齐对应缺口**（原"C++ 对象图缺失"措辞纠正，N44） | 指令说"读 60 格布局"，但运行时数据填的位置和指令期望的对不上 → 读**错位数据**（0x43ed8 处 std::vector 拷贝构造点读到未初始化 begin/end） | **读错位值 → 逻辑错乱**（非崩，是"值没对上"） |
| ③ 288MB PROT_NONE mmap | unidbg mmap2 mock 失败 → 大内存分配返**假指针** | **后续解引用越界** |

**"BL 解码"为什么"静态按段看对"还是算错？**（§124 ① 的机制）
- ARM `bl`（branch with link）= 跳目标地址 + 存返回地址到 lr，**PC 相对寻址**（目标 = PC+4 + 偏移）
- **静态**（`objdump`）按 PC 相对公式算 `bl` 目标，**永远对**（`bl 0x7965a → 0x10000004`）
- **动态（unicorn2 模拟器）**：模拟执行到 0x7965a 这条 `bl` 时，**它的 PC 计算有 off-by-2 精度问题**（dynarmic 后端对 Thumb `add rX,pc` 用 `(addr+4)&~3` mask，unicorn2 用 `(addr+4)` 不 mask，**与真 ARM 不一致**）→ 目标算错（跳 0x6eaea 非 0x10000004）
- **这是"模拟器精度 bug"，不是"so 跳错"也不是"静态段看错"**：unidbg 忠实执行了那条 `bl`，是 **unicorn2 模拟器算 PC 相对目标时和真 ARM 差 2 字节**（上下文相关，有的 `bl` 对、有的错）
- **军棋已修**（§124d）：切 Unicorn2 后端 + 修 PC off-by-2（`add rX,pc` 不 mask），实证 0xa37fc 存 0x159880 = 不 mask 值对上

**"常量池全是公开常量，没业务数据？"**（§124 ② 的"数据"到底缺什么）

通用代码常量池确实只有类型/库常量，**但军棋 so 的常量池里混着 4 类"非公开业务数据"**（N44 精确化：3 类在 so，1 类在资源文件）：

| 业务常量 | 在哪（精确） | 值怎么拿 | 语义怎么懂 |
|---|---|---|---|
| ① 38 子布局坐标 | **不在 so，在 `assets/data*.pak` 的 `.lay` 布局文件**（data 组 idx 47-58，30 字节/布局）；so 里只有"读布局的逻辑 + rank 序常量" | **SPAK 解包 + 布局解析**（比 so 常量多一层资源解包） | 逆向"哪 38 子摆哪格" |
| ② 地雷/炸弹阈值（70 步/1000 步判和） | **在 so 的 `.rodata`/常量池**（编译期烧进的 int 常量） | 静态反汇编读（`cmp rX,#1000` 立即数） | 逆向"累计 N 步判和"（0x30280 规则引擎） |
| ③ SPAK 解密 key（32B） | **在 so 的 `.rodata`/`.data`**（编译期烧进的 32 字节） | 静态 dump（`.rodata` 明文） | 逆向"这是解 SPAK 资源的 key" |
| ④ 蓝牙 UUID + 7 字段帧 | **UUID 字符串 + `v2\n%d,...` 格式串都在 so 的 `.rodata`（明文）** | 静态读 `.rodata`（`rodata_strings.txt` 1715 条里就有） | 逆向 7 字段语义（type/fc/fr/tc/tr/rank/side，OnBluetooth 解析） |

**关键区分（"非公开"≠"读不出"）**：
- **②③④ 的值在 `libjunqi.so` 里（`.rodata`/常量池，静态可 dump）**——**"非公开"指"语义不公开"**（值能读，含义要逆向：`0x4` 读出来是数字，"它代表炸弹"要 R-route 逆向）
- **① 的值根本不在 so，在资源文件（`.pak` 的 `.lay`）**——**比 so 常量还多一层"SPAK 解包"**，所以"apk 里静态可推七七八八"主要指 ①②③④ 都在 apk 里（so 或 .pak），**不是"运行时凭空不可知"**
- **dump 出数字 ≠ 读懂语义**（R-route 把"0x4→炸弹"这类映射逆向成明确业务规则，才叫"对齐原版"）
- **常量池总公式**：**常量池 = 数值（②③④ 在 so 里静态就能 dump、① 需先解包 .pak）+ 语义（要 R-route 逆向）**。"非公开"指语义层（值公开可读），**不是"值藏在 so 里读不出"**

**★ 三层分工（unidbg 方便 / frida 补齐 / 真机构造链填）**：
- **业务数据 apk 静态可推**（38 子布局在 `.lay` 文件 / so 常量池，SPAK key/蓝牙 UUID/阈值在 `.rodata` 明文）——**不用 unidbg 也能静态读七七八八**
- **unidbg 补"方便"**（补环境 + 重定位 + GLOB_DAT，让指令级跑通）——但**补不齐"数据与指令对齐"**（运行时内存布局没真实 C++ 构造链）
- **frida/redroid dump 补"真值"**（拿运行时指针/字段值）——但**跨进程指针带不回对象本身**（只带值，§〇e 实证）
- **真机 C++ 构造链填"真实布局"**（std::vector/list 真实布局只有真机跑出来才准）

**类比**：军棋有菜谱（指令，逆得出来）+ 食材清单（业务数据，apk 里静态有），**缺的是"厨师按菜谱把菜做好"那一步（运行时数据与指令对齐对应）**——unidbg/frida 能帮忙备料（补值/dump 真值），但"做好那盘菜"需真机 C++ 构造链。**不是"菜谱里没写菜名"（业务数据 apk 里有），是"菜没做好"（运行时对齐缺口）**。

**★ 交叉区分（N44，防和 C.1 混淆）**：ch02 这里纠的 **§124 ② "数据与指令对齐对应"是 unidbg 模拟路线的缺口**（业务数据 apk 静态可推，缺 unidbg/翻译体补不齐的**运行时内存对齐**）；**C.1 附录的"场景对象图全构造"是 32 位翻译体路线的缺口**（std::list node next / 场景对象 vtable / 0xbe9cc r0-r2 参数指针**运行时构造出来**，全量 4245 场景闭包也补不了"对象图数据"）——**两者相关（都是"代码对齐了但数据没对上"）但不相同**：
- ch02 §124 ② = "业务数据静态可推，缺**运行时对齐**"（unidbg 补环境视角，**数据本身 apk 里有**）
- C.1 = "场景对象图需**真实 C++ 构造链跑出来**"（翻译体视角，**数据是运行时 new 出来的**，std::list/vector 布局）
- **军棋 32 位 so 同时卡这两层**：外层"业务数据与指令对齐"（ch02）+ 内层"场景对象图构造"（C.1），**外层补了（gate-set texID 0→1）内层仍卡**（§124zz-4 红线）——**别把"业务数据 apk 可推"（外层，相对好补）误读成"场景对象图也能推"（内层，需真机构造链）**

**结论**：军棋"地址调用 + 18 常量注入"能推进 OnCreate 到 0x43ed8，
但"能玩"卡的是 §124 的数据与指令对齐对应（N44：不是"调不通"，是"调通了但数据没对上"——业务数据 apk 静态可推，缺运行时对齐 + 真机 C++ 构造链）。
## 本章小结（一句话版）

> "加载 so"只是把程序搬进房间，"调函数"还要**找入口、传参数、补环境**三步。
> 军棋 strip 后只能走**地址调用**（14 个 `On*` 入口 + `&~1` 对齐 Thumb 奇地址），
> 调通后卡在 **18 个 `.text` 常量的"房间真值"**（门牌号静态可读，房间真值静态读不出（N45）；早期需 redroid dump 72B 房间真值注入，**★ §124x-z 后 = 静态位移固化 `jqt_mem.c` `g_jq_got_tbl` 免 dump**）
> 和 **§124 三项阻塞**（① BL 解码 bug ② **数据与指令对齐对应缺口**（N44：业务数据 apk 静态可推，缺运行时对齐 + 真机 C++ 构造链，非"对象图不可知"） ③ 288MB mmap）——
> 指令能跑 ≠ 能玩。
>
> **双方向桥（本章最易混点，痛点 2 澄清）**：
> `Java_` 前缀导出符号是 **"Java 调 so"的门牌**（方向 ①，VM 加载 so 时按符号绑定 `Java_com_cnvcs_App_OnCreate` ↔ `com.cnvcs.App.OnCreate`，调用时直接跳 so 函数地址，unidbg 用 `call(0x233e1)` 模拟）；
> `JNIEnv*`（232 槽）是 **"so 调 Java"的中间层**（方向 ②，VM 提供的 JNI 标准 C API，C++ 实现在 libdvm/libart，**不是 Java 方法也不是 so 的函数**；so 通过 `env->FindClass` / `env->CallVoidMethod` 跳表间接访问 Java，unidbg 用 `getJNIEnv()` 模拟表 + `setJni` 应答实现，模拟环境没有真 libart）。
> **两方向独立**：so **被调**靠 `Java_` 导出符号，so **调 Java** 才靠 `JNIEnv*`。`jobject` 是方向 ② 里的 Java 对象句柄，跟 `JNIEnv*`（API 入口表）是两样东西。
