# 第二轮审计:所有章节"追问深度"重写规范

## 用户追问风格(本次对话沉淀)

用户在第 1 章追问链:
1. "unidbg 只支持 32 位?" → 拆成 32/64 两条路径 + 3 个 CPU 后端
2. "Java 是怎么模拟的?" → 拆成 4 环节(指令位宽/ELF 数据位宽/内存映射/系统调用拦截),每环节标"能干什么/不能干什么"
3. "为什么不直接翻译成 arm64?" → 路线 A(人工翻译黑屏)+ 路线 B(简化重写玩法不一致)
4. "运行时动态翻译保存下来不就转译指令了?" → 动态翻译产物依赖 QEMU 模拟状态,保存崩;人工翻译(路线 A)做过了,黑屏
5. "换 arm64 宿主机不就一样了?" → 拆"指令位宽 vs ELF 数据位宽"两个独立维度,换宿主只改指令位宽,不改 ELF 数据位宽
6. "值还是从 32 位真库读,跟宿主无关" → 确认重定位值来源(真实 32 位 libc.so),不是 unidbg 算的

## 重写每章必须满足的 5 条审计标准

1. **痛点段 2-4 个**:每个痛点"大白话卡点 + 为什么卡 + 不解决会怎样"
2. **为什么这样做:方案动机**:生活类比讲设计动机,且预判读者会追问"为什么不那样做",把追问点直接写进正文
3. **逐环节可操作**:每个技术环节(加载/重定位/Hook/JNI/...)都标"我们能干什么/不能干什么",用表格或"✓ 能做 / ✗ 不能做"
4. **军棋实战验证**:用 libjunqi.so 真实卡点/实测数据(12 init_array/5312 RELATIVE/214 PLT/6 GLOB_DAT/14 入口/7 依赖/0x43ed8/0x159880/0x233e1/§124 三项阻塞)验证
5. **篇幅 250-400 行**(原书每章几千字,课程"提炼但保留深度")
